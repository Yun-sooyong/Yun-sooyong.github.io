# 데이터베이스 서비스와 Business Logic 정리

## 개요

애플리케이션은 네트워크를 통해 데이터베이스 서버에 접속하고, SQL을 실행한 뒤 결과를 받아 비즈니스 로직으로 처리합니다.  
즉, 프로그램이 DB에 접속해서 데이터를 조회·변경하고, 그 결과를 서비스 규칙에 맞게 가공하는 구조

사용자 요청  
→ 애플리케이션 서버  
→ 비즈니스 로직 실행  
→ DB 연결  
→ SQL 실행  
→ 결과 반환  
→ 후처리  
→ 사용자 응답

---

## 1. DB 서버 구성

포함 요소:

- MySQL 서버
- 서버측 커서
- 방화벽
- 내부 네트워크 장비

의미:

- MySQL이 실제 데이터를 저장하고 관리한다.
- 커서는 조회 결과를 한 번에 모두 가져오지 않고 조금씩 가져오는 방식에 사용된다.
- 방화벽은 허용된 접속만 통과시켜 DB 보안을 담당한다.

---

## 2. 네트워크 연결 구조

포함 요소:

- 공인 IP
- 사설 IP 대역 (`192.168.8.0/24`)
- 여러 서버와 클라이언트
- Linux/CentOS 기반 서버 예시
- 라우터 또는 스위치 역할의 네트워크 장비

의미:

- 외부에서는 공인 IP로 접근한다.
- 내부 서버들은 사설 IP를 사용한다.
- 실제 DB 서버는 외부에 직접 노출하지 않고 내부망이나 방화벽 뒤에 두는 것이 일반적이다.
- DB 접속은 보통 TCP/IP 기반으로 이루어진다.

---

## 3. 애플리케이션의 DB 처리 흐름

처리 순서:

1. `Connect()` 로 DB 접속
2. `Cursor()` 생성
3. `Execute()` 로 SQL 실행
4. `fetchone`, `fetchmany`, `fetchall` 로 결과 조회
5. 프로그램 내부에서 `List`, `Dict`, `Tuple` 등 자료형으로 변환
6. 비즈니스 로직 처리 후 결과 사용

---

## 4. Connect

DB와 연결을 생성하는 단계

주요 접속 정보:

- host
- port
- username
- password
- database
- charset
- autocommit 설정

예시:
```python
conn = connect(  
    host="192.168.8.10",  
    port=3306,  
    user="app_user",  
    password="비밀번호",  
    database="shop",  
    autocommit=False  
)
```
### 알아둘 점

- MySQL 기본 포트는 보통 `3306`
- 운영 환경에서는 접속 정보를 코드에 직접 쓰지 않고 환경변수나 설정파일로 관리
- 작업이 끝나면 반드시 연결을 종료해야 함

---

## 5. Transaction / Autocommit

### 트랜잭션

여러 작업을 하나의 작업 단위로 묶는 것

예:
- 주문 생성
- 재고 차감
- 결제 정보 저장

이 세 작업은 하나의 트랜잭션으로 묶는 것이 일반적

### Autocommit

SQL 실행 후 자동으로 반영할지 여부

- `autocommit=True`  
    SQL 실행 즉시 반영
- `autocommit=False`  
    직접 `commit()` 해야 최종 반영 가능  
    오류 발생 시 `rollback()` 가능

### 실무 관점

- `INSERT`, `UPDATE`, `DELETE` 는 트랜잭션 관리가 중요
- 여러 SQL이 하나의 업무로 묶이면 `autocommit=False` 가 더 안전

---

## 6. Cursor

커서는 SQL 실행과 결과 처리를 담당하는 객체입니다.

주요 역할:

- `execute()` 로 SQL 실행
- `fetchone()`, `fetchmany()`, `fetchall()` 로 결과 조회
- `rowcount` 로 처리 건수 확인

---

## 7. Execute와 CRUD

SQL을 실제로 실행하는 단계입니다.

### CRUD

- **Create** → `INSERT`
- **Read** → `SELECT`
- **Update** → `UPDATE`
- **Delete** → `DELETE`

예시:
```SQL
INSERT INTO ...  
SELECT ...  
UPDATE ... SET ...  
DELETE FROM ...
```
---

## 8. Fetch 계열 메서드

### `fetchone()`

한 행만 가져옴

### `fetchmany(n)`

지정한 개수만큼 여러 행을 가져옴

### `fetchall()`

전체 결과를 한 번에 가져옴

### 실무 팁

- 데이터가 적으면 `fetchall()` 사용 가능
- 데이터가 많으면 `fetchmany()` 나 반복 조회가 유리
- 대용량 처리에서는 서버측 커서가 도움이 됨

---

## 9. 전송 타입과 자료형

DB 결과는 프로그램 내부에서 다양한 자료형으로 다뤄집니다.

### Tuple 방식

기본 커서 결과는 튜플 형태인 경우가 많습니다.

(1, "Kim", 25)

### Dict 방식

컬럼명을 키로 갖는 딕셔너리 형태로 받을 수도 있습니다.
```python
{"id": 1, "name": "Kim", "age": 25}
```
### List

여러 행을 가져오면 보통 리스트 안에 튜플 또는 딕셔너리가 들어갑니다.
```python
[  
  {"id": 1, "name": "Kim"},  
  {"id": 2, "name": "Lee"}  
]
```
### 실무 관점

- 빠르고 단순한 처리는 `tuple`
- 가독성과 유지보수는 `dict`
- API 응답 가공에는 `dict` 가 더 편리함

---

## 10. Business Logic

비즈니스 로직은 서비스의 업무 규칙을 처리하는 핵심 로직입니다.

예:

- 재고가 0이면 주문 불가
- 회원 등급에 따라 할인율 적용
- 결제 완료 시에만 배송 상태 변경
- 하루 최대 구매 수량 제한

정리하면:

- DB는 데이터를 저장하고 조회하는 역할
- Business Logic은 데이터를 어떻게 판단하고 처리할지 결정하는 역할

사용자 요청

### 예시: 쇼핑몰 주문 처리

1. 사용자가 주문 요청
2. 애플리케이션이 DB 접속
3. 재고 조회
4. 재고 충분 여부 판단
5. 주문 데이터 `INSERT`
6. 재고 수량 `UPDATE`
7. 문제 없으면 `COMMIT`
8. 오류 발생 시 `ROLLBACK`

## 12. 추가로 알아야 할 내용

### 12.1 연결 종료

DB 작업 후에는 자원을 반드시 정리해야 합니다.

- `cursor.close()`
- `connection.close()`

연결을 닫지 않으면:

- 연결 누수 발생
- 최대 접속 수 초과
- 성능 저하 가능

---

### 12.2 예외 처리

DB 작업에는 항상 오류 가능성이 존재함

예:
- 접속 실패
- SQL 문법 오류
- 무결성 제약 위반
- 트랜잭션 충돌
- 타임아웃

일반적인 처리 구조:
```python
try:  
    SQL 실행  
    commit()  
except:  
    rollback()  
finally:  
    cursor/connection 종료
```
---

### 12.3 SQL Injection 방지

문자열 결합으로 SQL을 만들면 매우 위험합니다.

위험한 방식:
```python
sql = f"SELECT * FROM users WHERE id = {user_input}"
```
안전한 방식:
```python
sql = "SELECT * FROM users WHERE id = %s"  
cursor.execute(sql, (user_input,))
```

핵심:
- 문자열로 SQL을 직접 이어붙이지 않기
- 반드시 파라미터 바인딩 사용

---

### 12.4 Connection Pool

요청마다 새 연결을 만들면 성능이 떨어지기 때문에 실무에서는 보통 커넥션 풀을 사용

장점:
- 연결 재사용
- 응답 속도 향상
- DB 부하 감소
- 안정적 접속 관리

---

### 12.5 인덱스와 성능

비즈니스 로직이 빨라도 SQL이 느리면 전체 서비스가 느려집니다.

중요 컬럼:
- `WHERE`
- `JOIN`
- `ORDER BY`
- `GROUP BY`

주의:
- 인덱스는 조회 성능을 높일 수 있음
- 너무 많으면 `INSERT`, `UPDATE`, `DELETE` 성능 저하 가능

---

### 12.6 서버측 커서와 일반 커서 차이

#### 일반 커서

- 결과를 한 번에 많이 가져옴
- 소량 데이터에 적합

#### 서버측 커서

- 서버가 결과를 유지하며 조금씩 전달
- 대용량 조회에 유리
- 메모리 사용량 절감 가능

---

### 12.7 권한 분리

DB 계정은 용도별로 나누는 것이 좋습니다.

예:

- 조회 전용 계정
- 일반 서비스 계정
- 관리자 계정

이유:

- 보안 강화
- 실수 방지
- 최소 권한 원칙 적용

---

### 12.8 DB 외부 직접 노출 금지

권장 구조:

- DB 서버는 내부망에 배치
- 애플리케이션 서버만 DB에 접근 가능
- 외부 사용자는 DB에 직접 접근하지 않음

이유:

- 공격 표면 감소
- 보안 강화
- 접근 제어가 쉬움

## 15. 예시 코드

```python
import pymysql  
  
conn = pymysql.connect(  
    host="192.168.8.10",  
    user="app_user",  
    password="password",  
    database="shop",  
    autocommit=False,  
    cursorclass=pymysql.cursors.DictCursor  
)  
  
try:  
    with conn.cursor() as cursor:  
        sql = "SELECT id, name, price FROM product WHERE id = %s"  
        cursor.execute(sql, (1,))  
        row = cursor.fetchone()  
  
        if row is None:  
            raise Exception("상품이 존재하지 않습니다.")  
  
        update_sql = "UPDATE product SET stock = stock - 1 WHERE id = %s AND stock > 0"  
        cursor.execute(update_sql, (1,))  
  
    conn.commit()  
  
except Exception as e:  
    conn.rollback()  
    print("오류 발생:", e)  
  
finally:  
    conn.close()
```

### 포함된 개념

- `connect()` : DB 접속
- `cursor()` : SQL 실행 준비
- `execute()` : SQL 실행
- `fetchone()` : 한 건 조회
- `DictCursor` : 결과를 딕셔너리로 받음
- `commit()` / `rollback()` : 트랜잭션 처리
- `close()` : 연결 종료
