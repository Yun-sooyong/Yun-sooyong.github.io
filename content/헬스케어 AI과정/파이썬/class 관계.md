# 관계와 설계

## 클래스와 자료구조의 관계

클래스는 **사용자 정의 데이터 타입**이며, 서로 다른 성격의 데이터를 하나로 묶어 표현할 수 있는 **자료구조 역할**도 합니다.

예를 들어 학생 정보를 표현할 때 이름, 학번, 점수처럼 서로 다른 데이터를 하나의 클래스로 묶을 수 있습니다.
```python
class Student:  
    def __init__(self, name, student_id, score):  
        self.name = name  
        self.student_id = student_id  
        self.score = score
```
이처럼 클래스는 **이질적인 데이터를 묶는 구조체적 역할**을 합니다.

### 클래스와 자료구조의 결합

클래스는 다른 자료구조와 함께 자주 사용됩니다.

- `list`에 클래스 객체를 저장할 수 있음
- `dict`의 값으로 클래스 객체를 저장할 수 있음
- 클래스의 멤버변수로 `list`, `dict`를 가질 수 있음

예:
```python
class Classroom:  
    def __init__(self):  
        self.students = []   # Student 객체들을 저장하는 list
```
즉,

- **자료구조 안에 클래스 객체를 넣을 수 있고**
- **클래스 내부에 자료구조를 둘 수도 있습니다**

이 구조를 이용하면 복잡한 현실 세계의 관계를 코드로 잘 표현할 수 있습니다.

---

## 클래스 간의 관계

클래스와 클래스 사이에는 여러 종류의 관계가 있습니다.

---

### 1. 의존(Dependency)

의존은 한 클래스가 다른 클래스를 **잠깐 사용**하는 관계입니다.  
주로 메서드의 매개변수, 지역변수, 리턴값 등으로 다른 클래스가 등장합니다.

즉, **필요할 때만 잠시 빌려 쓰는 관계**입니다.
```python
class Printer:  
    def print_book(self, book):  
        print(book.title)  
  
class Book:  
    def __init__(self, title):  
        self.title = title
```

여기서 `Printer`는 `Book`을 멤버로 가지지 않고, 메서드에서 잠깐 사용하므로 **의존 관계**입니다.

---

### 2. 연관(Association)

연관은 한 클래스가 다른 클래스 객체를 **멤버변수로 참조하여 지속적으로 관계를 유지**하는 것입니다.

즉, **계속 알고 지내는 관계**입니다.
```python
class Teacher:  
    def __init__(self, name):  
        self.name = name  
  
class Student:  
    def __init__(self, name, teacher):  
        self.name = name  
        self.teacher = teacher
```
학생은 선생님 객체를 멤버변수로 가지고 있으므로 `Student`와 `Teacher`는 **연관 관계**입니다.

---

### 3. 집합(Aggregation)

집합은 연관 관계의 한 형태로, **전체와 부분**의 관계를 나타냅니다.  
하지만 전체 객체가 사라져도 부분 객체는 독립적으로 존재할 수 있습니다.

즉, **느슨한 결합**입니다.

예: 도서관과 책
```python
class Book:  
    def __init__(self, title):  
        self.title = title  
  
class Library:  
    def __init__(self):  
        self.books = []
```
책은 도서관이 없어져도 존재할 수 있으므로 **집합 관계**입니다.

참고로,  
“연관이 여러 개면 집합이다”라고 단순히 보면 조금 부정확합니다.  
핵심은 **개수가 여러 개냐가 아니라, 전체-부분 관계이며 부분이 독립 생존 가능한가**입니다.

---

### 4. 포함(Composition)

포함은 집합보다 더 강한 관계입니다.  
한 클래스가 다른 클래스의 객체를 **직접 생성하고 소유**하며, 전체가 없어지면 부분도 함께 의미를 잃습니다.

즉, **강한 결합**입니다.

예: 사람과 심장
```python
class Heart:  
    pass  
  
class Person:  
    def __init__(self):  
        self.heart = Heart()
```
`Heart` 객체가 `Person` 안에서 생성되므로 **포함 관계**입니다.

핵심은:

- 내부 객체를 바깥에서 따로 만들지 않고
- 전체 객체가 부분 객체를 강하게 소유한다는 점입니다

---

### 5. 상속(Inheritance)

상속은 **is-a 관계**입니다.  
자식 클래스가 부모 클래스의 속성과 메서드를 물려받아 확장합니다.
```python
class Animal:  
    def speak(self):  
        print("소리를 냅니다")  
  
class Dog(Animal):  
    def bark(self):  
        print("멍멍")
```
`Dog`는 `Animal`의 한 종류이므로 **상속 관계**입니다.

정리하면 상속은:

- 공통 기능을 부모에 정의하고
- 자식이 이를 재사용하거나 확장하는 방식입니다

추가로, “부모는 자식을 가리킬 수 있다”는 말은  
보통 **다형성(polymorphism)** 맥락에서 쓰입니다.  
즉, 부모 타입 변수로 자식 객체를 참조할 수 있다는 뜻입니다.

---

### 6. 구현(Realization)

구현은 **인터페이스나 추상 클래스에 선언된 기능을 실제로 완성하는 관계**입니다.

즉, **can-do 관계**라고 볼 수 있습니다.

파이썬에서는 인터페이스 전용 문법은 없지만, 추상 클래스를 통해 비슷하게 표현할 수 있습니다.
```python
from abc import ABC, abstractmethod  
  
class Animal(ABC):  
    @abstractmethod  
    def sound(self):  
        pass  
  
class Cat(Animal):  
    def sound(self):  
        print("야옹")
```
`Cat`은 `Animal`의 추상 메서드 `sound()`를 반드시 구현해야 하므로 **구현 관계**입니다.

---

## 클래스 간 연산

클래스와 클래스 사이에서는 연산자 오버로딩을 통해 객체끼리 연산할 수 있습니다.

예:
```python
class Point:  
    def __init__(self, x, y):  
        self.x = x  
        self.y = y  
  
    def __add__(self, other):  
        return Point(self.x + other.x, self.y + other.y)
```
이렇게 하면 객체끼리 `+` 연산이 가능해집니다.

p1 = Point(1, 2)  
p2 = Point(3, 4)  
p3 = p1 + p2

즉, 클래스는 데이터만 저장하는 것이 아니라 **객체 간의 의미 있는 연산**도 정의할 수 있습니다.

# 디자인 패턴

디자인 패턴은 자주 등장하는 설계 문제에 대한 **검증된 해결 방식**입니다.

보통 다음 세 가지로 나눕니다.

---

## 1. 생성 패턴(Creational Pattern)

객체 생성 방식을 다룹니다.

예:

- **Factory Pattern**: 객체 생성 방식을 캡슐화
- **Singleton Pattern**: 프로그램 전체에서 객체를 하나만 생성

예를 들어 운영체제(OS)에 따라 다른 객체를 생성해야 할 때 Factory를 사용할 수 있습니다.

---

## 2. 구조 패턴(Structural Pattern)

클래스나 객체를 조합하여 더 큰 구조를 만드는 방법입니다.

예:
- **Adapter**
- **Decorator**
- **Facade**
- **Composite**

적어주신 내용 중 “전략구조”는 보통 **전략 패턴(Strategy Pattern)** 을 말하는데,  
이건 일반적으로 **행위 패턴**으로 분류됩니다.  
즉, “구조 패턴”으로 보기보다는 **행위를 바꾸는 패턴**으로 보는 것이 맞습니다.

---

## 3. 행위 패턴(Behavioral Pattern)

객체 사이의 책임 분배와 상호작용 방식을 다룹니다.

예:
- **Strategy**
- **Observer**
- **Command**
- **State**

적어주신 `Facade`는 보통 **행위 패턴이 아니라 구조 패턴**입니다.  
왜냐하면 복잡한 하위 시스템을 감추고, 단순한 인터페이스를 제공하는 **구조적 단순화**에 가깝기 때문입니다.

---

## 리팩토링(Refactoring)

리팩토링은 프로그램의 **기능은 바꾸지 않고**,  
코드 구조를 더 좋게 개선하는 작업입니다.

즉,

- 가독성 향상
- 유지보수성 향상
- 중복 제거
- 패턴 적용

등을 위해 내부 구조를 정리하는 과정입니다.

따라서  
“디자인 패턴에 맞춰 완성된 프로그램을 수정하는 것”도 리팩토링의 한 예가 될 수 있지만,  
리팩토링의 의미가 그것으로 한정되지는 않습니다.

# UML (Unified Modeling Language, 통합 모델링 언어)

UML은 소프트웨어 시스템의 구조와 동작을 **시각적으로 표현**하기 위한 표준 모델링 언어입니다.

## 1. 구조적 다이어그램

시스템의 **정적인 구조**를 표현합니다.

### 1) 클래스 다이어그램

클래스, 속성, 메서드, 클래스 간 관계를 나타냅니다.

### 2) 객체 다이어그램

특정 시점에서 실제 생성된 객체들의 관계를 보여줍니다.

### 3) 배치 다이어그램

소프트웨어와 하드웨어가 실제로 어떻게 배치되는지 표현합니다.

### 4) 복합체 구조 다이어그램

클래스 내부의 구성 요소와 상호작용 구조를 보여줍니다.

### 5) 패키지 다이어그램

클래스나 모듈들을 패키지 단위로 묶어 의존 관계를 표현합니다.

---

## 2. 행위적 다이어그램

시스템의 **동적인 동작**을 표현합니다.

### 1) 유스케이스 다이어그램

사용자와 시스템의 기능적 상호작용을 표현합니다.

### 2) 시퀀스 다이어그램

객체들이 시간 순서에 따라 메시지를 주고받는 흐름을 나타냅니다.

### 3) 커뮤니케이션 다이어그램

객체 간 연결 관계와 메시지 흐름을 중심으로 표현합니다.

### 4) 상태 다이어그램

객체의 상태 변화와 상태 전이를 표현합니다.

### 5) 활동 다이어그램

작업 흐름이나 절차를 순서도처럼 표현합니다.

### 6) 타이밍 다이어그램

시간 변화에 따른 객체 상태 변화나 상호작용을 나타냅니다.
